# Bitácora de trabajo - 2026-09-27

Recuperación de la automatización tras la caída de Supabase y ajustes para que
no vuelva a ocurrir.

## Síntoma

- Desde el 2026-09-26 todas las ejecuciones de `pulso-transmi-pipeline` y
  `pulso-transmi-model-drift` fallaban en el primer acceso a Supabase con
  `HTTP 503` y el código `PGRST002` ("Could not query the database for the
  schema cache").
- El dashboard en Vercel mostraba "Sin modelo" y las secciones de drift vacías.

## Diagnóstico

- La Management API de Supabase reportaba `db: UNHEALTHY` mientras `pooler` y
  `auth` estaban sanos: la API REST no alcanzaba Postgres.
- `GET /v1/projects/{ref}/config/disk/util` mostró `fs_avail_bytes: 0` sobre un
  disco de 2 GB: **el disco de la base estaba lleno**.
- El proyecto está en plan free, así que el disco no se puede ampliar.
- Un reinicio (`POST /v1/projects/{ref}/restart`) dejó Postgres en
  `recovery mode` sin poder terminar, porque no había espacio para escribir.

### Causa raíz

- Un job de cron-job.org disparaba `pipeline.yml` cada 5 minutos
  (`workflow_dispatch`, 916 ejecuciones).
- Cada ejecución reentrena, y como los datos crecen, el artefacto cambia y se
  registra un modelo nuevo. Por cada modelo se guardaban:
  - el artefacto comprimido en `model.artifact_base64` (~1 MB);
  - unas 10.000 predicciones de evaluación en `prediction`;
  - unas 10.000 filas en `monitoring_metric`, todas con la misma métrica.
- Todo eso se escribía **antes** de comprobar si había un ciclo de predicción
  abierto, de modo que también las ejecuciones que luego terminaban en
  `WAITING_FOR_OPEN_CYCLE` sumaban datos. Nada se borraba nunca.

## Recuperación

- Se creó un proyecto Supabase nuevo, **proyecto #2**
  (`kfkrtngrpvbgdluvwcnc`, us-east-1).
- Se aplicaron en orden todas las migraciones de `supabase/migrations/`.
- Se actualizaron `SUPABASE_URL` y `SUPABASE_SERVICE_ROLE_KEY` en los Secrets de
  GitHub, en las variables de entorno de Vercel y en el `.env` local.
- La primera ejecución volvió a cargar desde la API de Pulso el histórico
  completo: 12 estaciones, 51.840 observaciones de demanda y 4.320 de contexto.
- Se pierde el historial del proyecto anterior (ejecuciones, chequeos de drift y
  copia de predicciones enviadas). Las submissions siguen registradas en la API
  de Pulso, que es la fuente oficial.

## Verificación

- 18 pruebas pasan en local y en el workflow `ci`.
- Ejecución disparada por cron-job.org: ingesta incremental, entrenamiento
  (MAE 48,17; WAPE 0,1318) y poda de 10.368 predicciones y 10.368 métricas del
  modelo anterior.
- Workflow de drift: `alert=False`, `retrain=False`, compuerta de rendimiento
  `pass` (ratio WAPE 0,96) y publicación confirmada por la API para el ciclo
  `cyc_official-20260921_20260915T160000Z`.
- El dashboard (`https://desplegarmod.vercel.app`) muestra modelo activo,
  rendimiento, drift y última publicación.

## Operación

- Una ejecución en rojo que termina con `PIPELINE WAITING_FOR_OPEN_CYCLE`
  (código 2) es esperada: no hay ciclo abierto y se reintenta en la siguiente
  ejecución.
- La API del dashboard cachea su respuesta 5 minutos (`revalidate = 300`).
- Uso de disco: `GET /v1/projects/kfkrtngrpvbgdluvwcnc/config/disk/util` en la
  Management API de Supabase.

## Pendiente

- Pausar o borrar el proyecto Supabase anterior (`crrwxwundpbjgismeryn`) cuando
  se confirme que ya no se necesita.
- Recomendado: disparar `model_drift.yml` desde cron-job.org y retirar su
  `schedule`, porque el de GitHub corre con horas de retraso.
- **Versionado en MLflow no efectivo todavía.** Sin `DAGSHUB_REPO_OWNER`,
  `DAGSHUB_REPO_NAME` (Variables) y `DAGSHUB_TOKEN` (Secret) en GitHub, cada job
  usa un `mlflow.db` temporal: todos los modelos quedan como
  `mlflow_model_version = 1` y los artefactos de modelos retirados no se pueden
  recuperar. El versionado en Supabase (`model.version` por hash del artefacto,
  `status` active/retired, `code_commit`, `training_run`) sí funciona.
