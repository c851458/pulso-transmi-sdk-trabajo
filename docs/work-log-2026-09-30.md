# Bitácora de trabajo - 2026-09-30

Reentrenamiento automático del modelo: primero en un loop de una hora y,
el mismo día, reemplazado por un reentrenamiento que solo ocurre cuando la
accuracy baja de 79 % (ver la sección final).

## Situación anterior

- cron-job.org dispara `pipeline.yml` cada 10 minutos (`workflow_dispatch`).
- Cada ejecución de `python -m src.pipeline` reentrenaba el modelo, así que el
  modelo se reentrenaba unas 6 veces por hora. Cada modelo nuevo registra
  artefacto, `training_run` y predicciones de evaluación en Supabase (acotadas
  por `prune_model_history`, ver `docs/work-log-2026-09-27.md`).

## Cambio

El pipeline sigue ejecutándose cada 10 minutos, pero reentrena como máximo una
vez por hora:

1. Al iniciar, `src.pipeline` lee el modelo activo de Supabase
   (`status = active`, incluido su `trained_at`).
2. `retrain_due()` decide:
   - **reentrenar** si no hay modelo activo, si no tiene `artifact_base64` o si
     `trained_at` tiene al menos `RETRAIN_INTERVAL_HOURS` de antigüedad;
   - **no reentrenar** en otro caso: restaura el artefacto activo desde
     Supabase y publica las predicciones con él (el mismo camino que
     `--publish-only`). En el log aparece
     `Active model is younger than 1h; skipping retraining`.
3. Un reentrenamiento registra un modelo nuevo con `trained_at` actual, lo que
   reinicia el reloj de la siguiente hora.

| Cambio | Archivos |
| --- | --- |
| `retrain_due()` y variable `RETRAIN_INTERVAL_HOURS` (por defecto `1`). Nueva opción `--force-retrain` que omite la compuerta. | `src/pipeline.py` |
| `active_model()` devuelve también `trained_at`. | `src/supabase_resilience.py` |
| El paso de publicación pasa `RETRAIN_INTERVAL_HOURS` desde las Variables del repositorio y el input `force_retrain` de `workflow_dispatch`. | `.github/workflows/pipeline.yml` |
| Pruebas de la compuerta (sin modelo, modelo reciente, intervalo cumplido, fecha sin zona horaria). | `tests/test_retrain_schedule.py` |

Commit: `5a0f85f` ("Retrain the model at most once per hour in the pipeline").

## Configuración

| Qué | Dónde | Efecto |
| --- | --- | --- |
| `RETRAIN_INTERVAL_HOURS` | GitHub → Settings → Secrets and variables → Actions → **Variables** | Horas mínimas entre reentrenamientos. Sin definir vale `1`. Admite decimales (`0.5` = 30 min). |
| `force_retrain` | Actions → `pulso-transmi-pipeline` → Run workflow | Reentrena en esa ejecución aunque el modelo tenga menos de una hora. |
| `--force-retrain` | `python -m src.pipeline --force-retrain` en local | Igual que el anterior. |

No se agregó `schedule` a `pipeline.yml`: el disparador sigue siendo
cron-job.org, para no duplicar ejecuciones.

## Comportamiento esperado

- De cada ~6 ejecuciones por hora, una reentrena y las demás solo publican.
- El reentrenamiento ocurre en la primera ejecución después de cumplirse la
  hora, por lo que puede retrasarse hasta un intervalo de cron-job.org
  (~10 minutos) más la latencia de GitHub Actions.
- Menos modelos nuevos por hora implica menos escrituras y podas en Supabase.

## Relación con el drift

`model_drift.yml` no cambia: sigue reentrenando cuando detecta drift, con su
propio `RETRAIN_COOLDOWN_HOURS` (24 h). Un reentrenamiento por drift también
actualiza el modelo activo y, por tanto, reinicia el reloj del loop horario.

## Limitación conocida

Si un reentrenamiento produce un artefacto idéntico al del modelo activo (mismo
hash), `publish()` reutiliza el modelo existente sin actualizar `trained_at`, y
la ejecución siguiente vuelve a reentrenar. Con datos nuevos cada 10 minutos es
poco probable.

## Cambio posterior: reentrenar solo si la accuracy baja de 79 %

El loop horario reentrenaba aunque el modelo estuviera bien, y los datos
mostraron que cada reentrenamiento producía exactamente el mismo modelo
(WAPE 13,18 % en los 285 modelos): las observaciones en Supabase terminan el
2026-09-09 y no cambian entre ejecuciones. Ahora el criterio es la accuracy.

### Cómo se mide

`src/accuracy.py` calcula `accuracy = 100 × (1 − WAPE)` del modelo activo en
la ventana más reciente de datos observados (`ACCURACY_WINDOW_DAYS`, 7 días):

1. **`forecast`**: pronósticos enviados a la API (`prediction.actual_value`
   nulo) cruzados con la demanda observada después para la misma estación y
   hora. Es la accuracy real en producción.
2. **`evaluation`** (respaldo): predicciones de evaluación del modelo cuyo
   objetivo cae en esa ventana, las mismas que usa el control de drift.

Se exige un mínimo de `ACCURACY_MIN_ROWS` (96) filas. Hoy se usa
`evaluation`, porque los pronósticos apuntan al 15-18 de septiembre y aún no
hay demanda observada para esas fechas; cuando la API publique esas
observaciones, la medida pasa sola a `forecast`.

### Decisión

| Situación | Resultado |
| --- | --- |
| Sin modelo activo o sin artefacto | Reentrena |
| Accuracy no disponible | No reentrena (publica con el modelo activo) |
| Accuracy ≥ `RETRAIN_ACCURACY_THRESHOLD` (79) | No reentrena |
| Accuracy < 79 y modelo con menos de `RETRAIN_INTERVAL_HOURS` (1 h) | No reentrena todavía |
| Accuracy < 79 y modelo con 1 h o más | Reentrena |

El intervalo mínimo evita reentrenar cada 10 minutos si un reentrenamiento no
recupera la accuracy (el problema que llenó el disco el 2026-09-27).

- `pipeline.yml`: aplica la tabla en cada ejecución. El log muestra
  `Recent accuracy 86.76% (source=evaluation, rows=8076)` y
  `Skipping retraining: accuracy 86.76% >= 79%`.
- `model_drift.yml`: `retrain=true` solo si la accuracy baja de 79 % fuera de
  `RETRAIN_COOLDOWN_HOURS`; PSI y ratio de WAPE siguen como alertas
  informativas. Guarda `performance.accuracy` y `performance.accuracy_source`
  en `model_drift_check`. Su paso de reentrenamiento llama al pipeline con
  `--force-retrain`, porque la decisión ya está tomada.
- Dashboard: la tarjeta "Accuracy reciente" y su histograma muestran esta
  medida y el umbral.
- `force_retrain` en `workflow_dispatch` sigue forzando un reentrenamiento.

Valor al aplicar el cambio: modelo #285, accuracy 86,76 % → no reentrena.

## Reentrenamiento forzado y activación del modelo robusto

Ejecución `36776346079` de `pulso-transmi-pipeline` (commit `f2a046f`,
`force_retrain=true`, 20:58 UTC):

- Se seleccionó `drift_robust_ensemble`: MAE test 46,46, RMSE en línea con el
  anterior, WAPE 12,71 %, **accuracy 87,29 %** (antes 86,82 %).
- Se registró como modelo **#286** `drift_robust_ensemble-303ab30ff133`
  (activo desde las 21:01 UTC); el #285 quedó `retired` y la poda de historial
  terminó bien. Artefacto comprimido: 2,2 MB → 0,87 MB.
- El envío a la API falló con `HTTP 409 idempotency_conflict`.

### Causa del 409

El pipeline usa el `cycle_id` como clave de idempotencia: un solo envío por
ciclo. El ciclo `cyc_official-20260921_20260918T040000Z` ya lo había enviado
el modelo #285 a las 20:51 (`sub_d4f9ad9f672f40429a112c5dc2de9304`); el modelo
nuevo produce otras predicciones y la API rechaza un segundo contenido con la
misma clave. La API conserva el primer envío.

No es nuevo: con el reentrenamiento cada 10 minutos, cada modelo nuevo
intentaba reenviar el ciclo abierto, y parte de las ejecuciones rojas del día
eran este 409 y no `WAITING_FOR_OPEN_CYCLE`. Además, cada intento sobrescribía
la fila de `pipeline_execution` del ciclo (misma `run_id`) y la dejaba en
`failed`, aunque conservaba el `api_submission_id` del envío aceptado.

### Corrección (`src/pipeline.py`)

- Antes de preparar el envío se lee la fila del ciclo. Si ya fue aceptado
  (`status = confirmed` o con `api_submission_id`) con otro `payload_sha256`,
  no se reenvía ni se sobrescribe la fila.
- Si la API responde `409 idempotency_conflict`, se trata igual.
- En ambos casos el pipeline termina en verde con
  `PIPELINE CYCLE_ALREADY_SUBMITTED` y deja `pipeline_sync_status` en
  `SUCCESS`. Un modelo nuevo envía a partir del siguiente ciclo.
- Pruebas en `tests/test_retrain_schedule.py`.

Pendiente: las filas históricas de `pipeline_execution` afectadas siguen en
`failed` con el `model_id` del intento posterior, aunque la API aceptó el
envío original (`api_submission_id` presente).
